# 数学建模用户思路十问

## 唯一使命

本 Skill 是**面向用户的建模思路采集门禁**，不是 Agent 的审查清单。

用户上传题目和附件后，先依据材料定制问题，再向用户一次性提出**恰好 10 个必须回答的问题**。这些问题用于让用户明确自己的理解、偏好、取舍和约束，并把答案作为后续建模方案的输入。

本 Skill 不负责形成完整模型、不评价 Agent 已有方案、不编写代码，也不允许在内部推理中自行回答这 10 个问题。

## 触发时机

满足以下条件时立即调用：

- 用户刚提供一份新的数学建模题目或题目附件；
- 题面已经能够读取，可以识别基本任务与附件；
- 尚未开始详细拆题、选模、写公式或生成建模报告。

在完整工作流中，本 Skill 必须位于 `$mathmodel-analysis` 之前。直接调用 `$mathmodel-analysis` 处理新题时，也必须先完成本 Skill。

若用户明确要求跳过访谈，可以尊重，但必须说明后续方案将缺少用户偏好输入。已有项目恢复、纯代码实现、论文写作或最终验收不自动重新触发本 Skill。

## 提问前允许做的事

仅做定制问题所需的最小读取：

1. 读取题面、附件说明和提交要求。
2. 识别实际顶层问题、数据类型、显著歧义和可能的决策点。
3. 区分“材料中已有答案的事实”与“必须由用户表达的理解或偏好”。
4. 读取 [QUESTION-DIMENSIONS.md](references/QUESTION-DIMENSIONS.md)，据此构造本题专属的 10 个问题。

不得在此阶段生成完整建模路线、确定主模型、替用户选择假设或输出“自检结果”。材料中能查到的事实不应拿来考用户；应把问题名额用于用户的判断与思路。

## 强制十问协议

每次首次访谈必须同时满足：

- 一次性提出恰好 10 个编号问题，编号固定为 1–10；
- 每题都直接称呼并要求用户作答，问题必须与当前题目具体内容关联；
- 每题说明“为什么要问”或“答案会影响什么”；
- 可以给互斥选项帮助用户思考，但不得替用户勾选，也不得给可被一键接受的默认答案；
- 用户可以回答“不确定”，但这仍必须是用户对该题的显式回答；
- 要求用户按 1–10 逐题回复，不接受“你看着办”“全部按推荐”作为完整回答；
- 发出问题后立即暂停，等待用户回答。在收到 10 项回答前，不继续详细分析、建模、编码或写论文。

推荐输出格式：

```markdown
## 建模思路十问（请逐题回答）

请按 1–10 回复；暂时没有想法的题可以写“不确定”，但请不要省略编号。

1. <针对本题的具体问题>
   为什么要问：<会影响的解释、模型、数据处理、目标或验证>
...
10. <针对本题的具体问题>
    为什么要问：<影响>
```

## 明确禁止

- 禁止 Agent 在提问后自行模拟用户回答。
- 禁止把 10 个问题仅放入内部推理、报告或检查清单而不展示给用户。
- 禁止先完成一套方案，再用这 10 题验证 Agent 自己的方案。
- 禁止因“题面清楚”“已有常规做法”而少问、跳过或自动通过。
- 禁止提供 10 个推荐答案并让用户用“全部接受”结束访谈。
- 禁止把事实核对、格式检查、代码测试等 Agent 自检工作伪装成用户问题。

## 处理用户回答

收到回复后先检查编号 1–10：

1. 若有缺答，只列出缺失或含糊的编号并继续等待；不得自行补齐。
2. 若 10 项齐全，简洁复述用户的关键选择，区分“明确决定”和“用户尚不确定”。
3. 若答案彼此冲突，指出具体冲突并只追问解决冲突所需的问题；不得悄悄替用户裁决。
4. 创建或更新 `<WORK_ROOT>/reports/MODEL_GRILL_REPORT.md`，按 [REPORT-FORMAT.md](references/REPORT-FORMAT.md) 保留问题、原意回答与后续约束。
5. 将完整回答交给 `$mathmodel-analysis`；对于用户回答“不确定”的项目，由分析阶段提出候选方案和利弊，但不得冒充用户决定。

完成本 Skill 的条件不是“Agent 认为方案没问题”，而是“用户已经对 1–10 全部给出显式回答，且回答已被记录并传入后续分析”。
