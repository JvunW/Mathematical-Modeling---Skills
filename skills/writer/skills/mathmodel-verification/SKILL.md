# 验证和验收（Typst / LaTeX / Word）

本 skill 是完整工作流的最后一关。它不重新建模、不生成新结果、不代替写作阶段重写论文；它负责发现硬错误、修复可直接修复的问题，并输出 `reports/VERIFY_REPORT.md`。

## 数学建模规范参考

如需额外的数学建模领域规范，并且 `$mathmodel-references` 已随建模手插件安装，可调用它查询“论文验收与一致性”。未安装建模手插件时不得因此阻塞验收；具体目录、入口文件、结果文件和图表目录由当前任务结构决定。

## 阶段边界

- 本阶段负责：结构验收、文本质量门禁、图表引用检查、结果一致性检查、Typst/LaTeX 编译或 Word 导出检查、PDF/DOCX 视觉检查、提交清单。
- 本阶段不负责：重新设计模型、重新跑大规模实验、重新组织整篇论文。
- 发现硬错误时，优先做小范围修复；如果需要回到前序阶段，写入 `reports/VERIFY_REPORT.md` 并标记为未通过。

## 输入

由模型先根据当前工作区判断项目布局，再把实际路径传给检查脚本。常见输入包括但不限于：

1. 论文入口文件：`main.typ`（Typst）或 `main.tex`（LaTeX）。
   Word 交付使用 `paper.md` 等实际 Markdown 源文件和最终 `.docx`。
2. 正文章节目录或若干正文文件（`.typ` 或 `.tex`）。
3. 参考文献文件（`references.typ` 或 `references.tex`）。
4. 前序阶段的分析、建模、结果、图示报告。
5. 图表目录
6. 可复现代码目录。
7. 编译后的 PDF，或可由入口文件编译得到的输出 PDF。
8. Word 交付时的最终 DOCX 和 `$export-math-docx` JSON 验证报告。

不要假设论文目录一定叫 `paper/`，也不要假设结果文件一定在项目根。若项目使用不同命名，按实际结构传参并在 `reports/VERIFY_REPORT.md` 中说明。

## 工作流程


### Step 1: 运行文本质量门禁

优先运行本 skill 的脚本。脚本按入口文件扩展名自动选择检查逻辑（`.typ` → Typst 检查，`.tex` → LaTeX 检查）：

```text
python "<SKILL_DIR>/scripts/writing_check.py" \
  --paper-dir "<PAPER_DIR>" \
  --main "<MAIN_FILE>" \
  --sections-dir "<SECTIONS_DIR>" \
  --references "<REFERENCES_FILE>" \
  --figures-dir "<FIGURES_DIR>" \
  --results-file "<RESULTS_FILE>"
```

把本 `SKILL.md` 所在目录解析为 `<SKILL_DIR>`。参数只在对应文件存在或项目需要时传入；可先运行 `python "<SKILL_DIR>/scripts/writing_check.py" --help`。不要把脚本路径、论文目录或文件名写死在验收逻辑中。Unix 环境也可选用保留的 `scripts/writing_check.sh` 做扩展检查，但跨平台 Python 检查器是默认入口。

脚本只扫描文本，不生成论文，也不编译 PDF。它的 `FAIL` 属于硬错误，必须修复后重跑。

Word 交付不要把 Markdown 强行传给上述脚本。应直接检查 Markdown 标题层级、占位符、内部路径、图片存在性、引用和关键数值，再调用 `$export-math-docx` 的验证脚本：

```text
python "<EXPORT_SKILL_DIR>/scripts/verify_omml.py" \
  "<OUTPUT.docx>" --source "<PAPER.md>" --report "<OMML_REPORT.json>"
```

验证结果必须为 `valid: true`，并且 `omml_total >= expected_source_formulas`。

### Step 2: 章节数量和标题顺序

**Typst 引擎**检查：

- 入口 `.typ` 文件中 `#include("...")` 的数量是否与实际正文结构匹配。
- include 顺序是否符合文件名前缀顺序，例如 `1_...`, `2_...`, `3_...`。
- 每个 section 是否有明确一级标题（`= 标题`，等号后有空格）。
- 标题顺序是否符合所选论文类型。

**LaTeX 引擎**检查：

- 入口 `.tex` 文件中 `\input{...}` 或 `\include{...}` 的数量是否与实际正文结构匹配。
- 章节顺序是否符合文件名前缀顺序。
- 每个 section 是否有 `\section{}` 或对应级别标题。

**Word 交付**检查：

- Markdown 标题顺序与实际子问题数量一致；
- 摘要、关键词、问题重述、假设、符号、模型、求解、检验、评价、结论和参考文献按比赛要求存在；
- 最终 DOCX 中的 Word 标题层级与 Markdown 层级对应。

通用检查（两种引擎）：

- 章节文件是否缺失、重复引用、未被引用。
- 如果题目不是三问，不强行要求三段问题章节；按 `ANALYSIS_MODELING_REPORT.md` 的子问题数量核对。
- CUMCM 入口只引用题目实际存在的问题章节；模板自带的多余问题文件不能继续被入口引用。

### Step 3: 图表和章节匹配

**Typst 引擎**检查：

- 图表目录中的 PDF 是否在正文中被引用。
- `#figure(image(...), caption: [...])` 的图片是否真实存在。图片路径必须相对于 `.typ` 文件。
- 数据图是否放在对应结果/分析章节，非数据流程图是否放在方法/总体思路章节。

**LaTeX 引擎**检查：

- `\includegraphics{}` 引用的图片文件是否真实存在。路径相对于 `.tex` 文件。
- `\caption{}` 是否存在。
- 数据图是否放在对应结果/分析章节。

**Word 交付**检查：

- Markdown 图片路径真实存在，并优先使用 PNG、JPEG 或 SVG；
- DOCX 中对应媒体文件已经嵌入，不是失效的本地绝对路径。

通用检查（两种引擎）：

- 连续图表之间是否有足够解释文字。
- caption 是否过长、过泛或与图意不一致。
- 图表编号、正文引用和章节语义是否一致。

不要生成 `*_typst_includes.typ` 或 `*_latex_includes.tex`；图表必须直接嵌在对应 section 中。

### Step 4: 写作质量和泄露检查

检查并修复：

- `TODO`、`PLACEHOLDER`、`待补充`、`待续写`、`示例数据` 等占位符。
- 论文正文出现内部工作流文件名、临时目录名、代码目录名或结果 JSON 路径。
- 过多列表式写作（Typst 中大量 `#list`、`enum`，LaTeX 中大量 `\begin{itemize}`、`\begin{enumerate}`）。
- 段落反复以"如图""由图""图 X 展示了"开头。
- 图表后没有解释、公式后没有变量含义、结论只报数不解释。

#### CUMCM 内容门禁

对 `sections/*problem*.tex` 或 `sections/*problem*.typ` 逐问检查内容最低契约。每个实际子问题至少应出现：模型公式/目标函数、算法或参数说明、一个真实结果表或图、解释该证据的段落，以及一个验证、稳定性、误差或适用边界证据。问题重述必须有背景和任务分解，问题分析必须按实际子问题展开；敏感性分析只有在模型适用时才要求，其他题型可用误差、稳定性或情景分析替代。缺少核心公式、真实结果证据或结果解释时判定为 `FAIL`，不能只保留 `WARN` 后交付。附录若只有运行命令和文件清单、没有完整源代码，也判定为内容不完整。

验收不能只依赖关键词命中。对每个问题文件记录去除注释、导言和空白后的正文长度、二级小节数量、公式数量、表格/图片数量以及结果解释段落数量；只有标题或正文极短时判定为 `FAIL`。把代码附录、封面、目录、参考文献和分页空白排除后，再判断正文是否达到结构完整。论文写作流程产生的 `reports/PAPER_CONTENT_PLAN.md` 必须存在并包含论点、证据文件、预期表/图和状态字段；缺失或字段不全时判定为 `FAIL`。若存在 `EVIDENCE_GAP`，正文必须出现相应的限制说明。

#### 数量与视觉门禁

编译后记录摘要页数、正文页数、附录页数、表格数和图数。CUMCM 电子版摘要原则上不超过一页，正文不得超过比赛当年官方上限；最终电子版不应包含目录、承诺书或编号专用页。表格数和图片数只用于发现重复或失衡，不设统一最低或最高数量。不得通过缩小字号或压缩间距掩盖内容缺口。检查表格是否为三线表、表题是否置于表上方、单位和小数精度是否统一、符号表是否居中、结果表是否接近版心、窄表是否被无意义拉伸、宽表是否超出版心或被 `resizebox` 压得过小、图表是否重复表达同一证据。检查表格横线是否只覆盖自然文字宽度而造成孤立窄线，表格是否使用过小字号或负间距补偿版式问题。颜色、字体和行距按项目默认风格检查可读性，不作为全国统一硬性规则；灰度打印后仍应能区分数据，避免渐变、装饰性背景和红绿唯一编码。

### Step 5: 数值和结果一致性

检查：

- 论文中的关键数值必须来自当前工作流声明的结果记录或结果 JSON。
- 目标函数值、误差指标、排名、权重、阈值、灵敏度结果不得与结果记录冲突。
- 如果存在汇总结果 JSON，抽取关键指标并确认论文正文中有对应结果。
- 公式中的符号应在符号说明或正文首次出现处解释。

发现数值冲突时，不要自行发明新结果；应回到结果记录或代码输出修正论文。

### Step 6: 引用和模板规范

检查：

- 参考文献文件是否存在，或模板是否采用了其他真实参考文献机制。
- 正文引用标记（Typst 的 `@label`/`#super`，LaTeX 的 `\cite{}`）是否能对应到真实参考文献。
- Word 交付的数字引用标记是否能对应到 DOCX 末尾的真实参考文献条目。
- 中文论文 caption、表题、摘要语言保持中文；英文论文保持英文。
- 选定的模板入口是否保留所选比赛模板的必要封面、摘要、编号、页眉页脚或提交格式。
- CUMCM 电子版入口是否从摘要开始，且没有目录、承诺书和编号专用页。
- 不要把模板结构误删成普通空白文档。


### Step 7: 编译

先检测命令是否可用；只有可用时才执行对应编译器。

**Typst 编译**：

```text
typst compile "<MAIN_FILE>" "<OUTPUT_PDF>"
```

**LaTeX 编译**：

```text
xelatex -interaction=nonstopmode "<MAIN_FILE>"
xelatex -interaction=nonstopmode "<MAIN_FILE>"
```

xelatex 需跑两遍解决目录和交叉引用。

**Word 导出**：

调用 `$export-math-docx` 从 Markdown 或 Pandoc 可解析的 LaTeX 源生成 DOCX。Word 路径不需要 Typst 或 XeLaTeX，但必须有 Pandoc 或 `pypandoc-binary`，并通过 OMML 结构验证。

编译失败必须修复语法、路径、图片引用或模板问题后重跑。编译通过后确认输出 PDF 非空。

### Step 8: PDF / DOCX 视觉检查

如果模型有视觉能力，必须把编译后的 PDF 每页导出为 PNG 并逐页查看。这个步骤用于发现纯文本扫描和编译器无法发现的版式错误。

优先使用本 skill 的跨平台脚本选择系统已有工具；不要为了视觉检查引入沉重依赖：

```text
python "<SKILL_DIR>/scripts/render_pdf_pages.py" "<OUTPUT_PDF>" --output-dir "<WORK_ROOT>/_tmp/pdf-pages" --dpi 160
```

脚本依次选择 `pdftoppm`、`mutool`、`magick`。若都不可用，记录视觉检查未运行，不要伪称已查看页面。

导出后逐页检查：

- 页面是否空白、缺页、页数异常或页面尺寸异常。
- 标题、摘要、正文、页眉页脚、页码是否被裁切或位置明显错误。
- 表格是否超出页边距，单元格文字是否重叠、溢出、被截断。
- 图片、图题、表题、公式、编号是否与正文重叠。
- 公式是否越界，长公式是否压到页边距或下一段文字。
- 列表、段落、脚注、参考文献是否出现异常大空白、重叠或孤立残行。
- 中文/英文/数学符号字体是否明显缺字、乱码或 fallback 异常。
- 封面、摘要页、目录、附录等模板关键页面是否保留比赛要求的视觉结构。

如果是模板转换或已有参考 PDF 的项目，还应将不同引擎的 PDF 都逐页导出 PNG，按页对比版式差异；页数或页面尺寸不一致必须记录为硬错误或明确说明原因。

如果模型没有视觉能力，必须在 `reports/VERIFY_REPORT.md` 中明确写出“未执行视觉检查”的原因，并至少完成 PDF 非空、页数、页面尺寸等可程序化检查。

Word 交付应使用当前 harness 可用的 DOCX 渲染器、LibreOffice 或 Microsoft Word 将最终 DOCX 渲染为页面后逐页检查。渲染工具缺失时，明确记录“DOCX 仅完成结构验证”，不得把 OMML XML 验证表述成视觉检查通过。

### Step 9: 写验收报告

创建 `reports/VERIFY_REPORT.md`：

```markdown
# 验证和验收报告

## 结论
PASS / FAIL

## 检查项
| 检查项 | 结果 | 说明 |
| --- | --- | --- |

## 章节结构

## 图表引用

## 数值一致性

## 文本质量门禁

## 编译

## PDF / DOCX 视觉检查

## Word OMML 验证

## 仍需处理的问题
```

只有当硬错误都修复、文本门禁通过、核心图表都引用、数值一致、编译通过或明确说明不可编译原因、视觉检查通过或明确说明无法执行原因时，才写 `PASS`。

## 硬错误标准

以下问题必须判定 `FAIL`：

- 缺少选定的论文入口文件（`main.typ` 或 `main.tex`）或核心正文。
- 论文入口引用的章节文件不存在。
- Typst 入口缺少 `#include`；LaTeX 入口缺少 `\input`/`\include`。
- 正文章节缺少一级标题（Typst `= ` 后缺空格，LaTeX `\section{}` 缺失）。
- 章节顺序明显错误或重复。
- 正文仍有占位符。
- 模板示例正文、示例数值或示例图表残留。
- 正文泄露内部工作流文件名。
- 引用的图片不存在。
- 关键数值与结果记录冲突。
- 编译器可用但论文编译失败。
- Word 交付中 `omml_total` 少于源公式数量，存在 MathML、原始 `$...$` 残留或 DOCX ZIP/XML 损坏。
- 编译后的 PDF 为空、缺页、页数异常或页面尺寸异常且无法解释。
- 视觉检查发现正文、表格、图片、公式、页眉页脚、页码等关键元素重叠、裁切、越界或乱码。

## 警告标准

以下问题可判定为 `WARN`，但应尽量修复：

- 未引用的备用图片。
- 某章节过短或明显不均衡，但尚未达到内容失败条件。
- caption 偏长。
- 参考文献偏少。
- 图表后解释文字不足。
- 视觉检查工具不可用，但已经记录原因并完成基础 PDF 元数据检查。
- 代码完整复现耗时过长，只做了轻量检查。
- 非核心风格问题，例如图表数量偏少或参考文献数量偏少。
- 附录只有命令/文件清单，没有本次运行所用的完整源代码。
